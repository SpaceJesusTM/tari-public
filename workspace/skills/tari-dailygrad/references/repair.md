# Repair an existing DailyGrad digest

Read [the main skill](../SKILL.md) first. Repair retries generated content that
failed in an existing run. It preserves the selected stories and their order,
successful summaries, existing lesson/recall material, and LeetCode exercise.
It does not select fresh news. The original archive remains; a repair produces
a new revision with the same run ID, date, and original generation timestamp.

Repair only when the user asks to fix or complete a digest. Noticing degradation
does not authorize it. Mention the option when useful; do not repair as a side
effect of reading or automatically repeat it.

First resolve the exact digest through `dailygrad_digest`, including a named
run/date. If its status is already `ok`, explain that no repair is needed. For
a degraded digest, use its returned values in exactly:

`dailygrad_repair({run_id:N,date:"YYYY-MM-DD",timeoutSeconds:570})`

Tell the user it can take a few minutes and call once. Repair requires its own
enabled capability. Local reread verification must confirm the reported revision
and preservation of the original content before calling it verified.

Report the outcome, run/revision, repaired story numbers or lesson, and material
items still in `remaining`:

| Outcome | Meaning |
| --- | --- |
| `repaired` | The generated content that had failed is now complete |
| `partial` | Some content was repaired; identify what remains |
| `unchanged` | No usable new content was produced; nothing was written |
| `nothing_to_repair` | Nothing remains that this operation can generate |

Explain `lesson_note` when the curriculum has moved on; repair will not insert
an out-of-order lesson. A missing LeetCode exercise is not generated by repair.
Unavailable source pages or insufficient source text may remain unresolved.

Report busy/cooldown without loops. After timeout, disconnect, or unverified
output, the outcome is unknown and work may still finish. Never retry
automatically: read that same run later and compare its revision and remaining
content. A retry is a new explicit request. This integration performs no posting
or publication, and a successful repair does not authorize either.
